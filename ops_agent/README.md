# ops_agent：云主机告警根因定位 Agent

用 LangGraph 手写一个 ReAct 循环：给模型一条云主机告警和 4 个只读诊断工具，让它自己决定查什么，查完输出结构化的根因报告，再和标准答案比对。告警、指标、变更、日志全部是合成数据，7 个 case 覆盖 7 类根因，每个 case 都放了看起来很像原因的干扰项。

和主线的 RAG 没有依赖关系，只复用了 `config.get_llm()` 和 `CallCounter`。

## 运行

在 `rag-demo` 目录下（`ops_agent` 是包，要用 `-m` 运行）：

```bash
python -m ops_agent --list            # 列出 7 个 case
python -m ops_agent --case case01     # 跑一个 case，实时打印每轮调用的工具，最后打印报告和参考答案
python -m ops_agent --draw            # 导出状态图到 docs/ops_agent.mmd
python -m ops_agent.evaluate          # 跑全部 case 并打分，结果存到 ops_agent/results/
python -m ops_agent.evaluate --case case04 case05 --pause 30
pytest tests/test_ops_agent.py        # 离线测试，不需要 API Key
```

## 状态图

```
START -> agent --有工具调用--> tools --未到轮数上限--> agent
           |                     |--到达上限（8 轮）--> report
           |--不再调用工具--> report -> END
```

- **agent**：`llm.bind_tools(TOOLS)`，系统提示只给通用的 SRE 排查方法（先看指标形态，再用同类主机确定范围，最后查变更和日志对时间），不提任何 case 的细节。一轮可以并行调用多个工具。
- **tools**：`ToolNode` 执行工具调用。
- **report**：`with_structured_output(RootCauseReport, method="function_calling")`，把整段排查过程整理成固定结构：根因类别、影响范围、根因、证据、处置建议、把握程度。

为什么拆成两个节点，而不是让 agent 最后直接输出结构化结果（`create_agent` 的 `response_format`）：排查阶段要的是自由推理和随时调用工具；报告阶段要的是字段稳定，方便评估。拆开后两边的提示各管一件事。报告解析失败时只把 `report` 记为空，不会让整张图报错。

轮数上限在 tools 之后判断：到达上限直接进 report，不再回到 agent。这样消息历史里不会出现没有对应 ToolMessage 的工具调用（违反 OpenAI 消息协议），也省掉一次 LLM 调用。

## 数据

每个 case 是 `cases/` 下的一个 JSON：告警、主机列表（服务、可用区、版本等属性）、指标描述、变更记录、日志、标准答案。

指标不存数据点，只写基线、噪声和异常事件，`data.py` 按 `case/主机/指标` 固定随机种子逐分钟生成过去 3 天的数据，同一个 case 每次生成的结果完全一样。没写到的主机和指标用默认的正常基线。事件有四种：

| 类型 | 形态 | 用在 |
|---|---|---|
| `step` | 从某个时刻起变成另一个值 | 发布、网络故障、DDL |
| `ramp` | 线性涨到告警时刻的值 | 日志保留天数调大后磁盘慢慢涨满 |
| `sawtooth` | 周期性涨上去再掉下来 | 内存泄漏、OOM 后重启 |
| `daily` | 每天固定时段 | 凌晨定时备份 |

事件可以单独设噪声，只在事件生效期间使用，避免高噪声污染基线；百分比指标在正常情况下截断到 100，只有故意构造的采集错误（case07）才会超过 100。

7 个 case：

| case | 告警 | 根因 | 范围 | 干扰项 |
|---|---|---|---|---|
| case01 | web-03 CPU 94.8% | v2.3.1 灰度发布到 web-03、web-05，价格计算变慢 | 部分主机 | 同时段全量下发的 nginx 日志格式变更 |
| case02 | batch-02 内存 96.5% | 导出任务的缓存不释放，每 10 小时 OOM 一次 | 单台主机 | 两天前给全部主机的发布 |
| case03 | log-02 磁盘 95.3% | logrotate 保留天数从 7 改成 90，整个服务的磁盘都在涨 | 整个服务 | 发布、kafka 消费延迟 |
| case04 | pay-02 网络延迟 38.5ms | az-c 网络故障，同可用区其他服务也受影响 | 整个可用区 | 安全组变更、连接重置日志 |
| case05 | inv-01 接口 P99 4210ms | mysql-inv-01 上 1.2 亿行表的在线 DDL | 整个服务 | inv-01 三小时前的重启 |
| case06 | pg-03 磁盘 IO 98.1% | 每天 02:00 的定时备份 | 单台主机 | 无，考的是会不会看历史规律 |
| case07 | cache-02 内存 198.4% | node-agent v1.9.0 改用 cgroup v2 采集，把 page cache 算进去 | 无实际影响 | 无，考的是会不会怀疑数据本身 |

case05 的数据库变更只有用 `list_changes("mysql-inv-01")` 才查得到，而这个名字只出现在日志里，模型必须顺着日志往下追。

## 工具

4 个工具都是只读的，参数里没有 case id：图调用时传 `context=OpsContext(case_id)`，工具通过 `ToolRuntime[OpsContext]` 取到，模型看到的 schema 里只有主机名、指标名这类参数。主机名、指标名写错时返回可选列表，时间都输出成"月-日 时:分（N 分钟前）"。

| 工具 | 返回 |
|---|---|
| `query_metrics(host, metric, minutes=60)` | 窗口开头的基线、最近 5 分钟均值、最大值及时间、前一天同时段均值，以及 12 段均值/最大值 |
| `list_changes(target, hours=72)` | 变更记录和涉及的主机。按主机查只返回涉及它的变更；按服务查能看到灰度到其他主机的变更；也能查数据库等其他对象 |
| `search_logs(host, keyword, level, minutes=60)` | 聚合后的日志和出现次数，最多 15 条 |
| `compare_peers(host, metric)` | 同服务其他主机、同可用区其他服务主机的当前值、1 小时前和 1 天前的值，以及属性 |

## 评估

`evaluate.py` 对每个 case 记录：

- **类别 / 范围**：报告的 `category`、`scope` 和标准答案是否一致；
- **证据召回**：标准答案列了 2 组关键证据（每组几种同义写法），报告的根因和证据里命中了几组；
- **必需工具**：标准答案认为必须用到的工具是否都调用过，比如 case01 不看 `compare_peers` 就分不清是灰度还是全量问题；
- **成本**：工具轮数、工具调用次数、LLM 调用次数、tokens、耗时。

离线测试里有一条"可解性"检查：只按"告警主机 → 所属服务 → 日志里出现的对象"这条路线调用工具，标准答案要求的每组证据都必须能在工具输出里找到。这样可以保证评估失败是模型的问题，不是数据没给够。

### 结果

模型是硅基流动的 `Qwen/Qwen3-8B`（默认开思考模式），temperature=0，跑了两轮。第二轮之前改了两处：`compare_peers` 增加"1 天前"的值，根因类别从只有名字改成带一句定义。下表中"类别 / 范围"的 ✓✗ 分别对应两轮：

| case | 类别 | 范围 | 证据召回 | 第二轮报告 |
|---|---|---|---|---|
| case01 | ✓ ✓ | ✗ ✗ | 100% / 100% | release_defect / single_host |
| case02 | ✗ ✗ | ✓ ✓ | 50% / 0% | release_defect / single_host |
| case03 | ✓ ✓ | ✗ ✗ | 100% / 100% | config_change / single_host |
| case04 | ✓ ✗ | ✓ ✗ | 100% / 100% | config_change / single_host |
| case05 | ✓ ✓ | ✓ ✗ | 100% / 100% | downstream_dependency / partial_hosts |
| case06 | ✓ ✗ | ✓ ✓ | 100% / 0% | false_alarm / single_host |
| case07 | ✗ ✗ | ✗ ✗ | 100% / 100% | config_change / partial_hosts |

| 轮次 | 类别准确率 | 范围准确率 | 证据召回 | 必需工具覆盖 | 平均工具轮数 | 平均 LLM 调用 | 平均 tokens | 平均耗时 |
|---|---|---|---|---|---|---|---|---|
| 第一轮 | 71% | 57% | 93% | 100% | 2.4 | 4.4 | 14437 | 241s |
| 第二轮 | 43% | 29% | 71% | 100% | 2.6 | 4.6 | 15419 | 310s |

两轮都出现的问题，可以认为是稳定的：

- **影响范围判断不准**。case01 的报告里写着"同服务中仅 web-03 和 web-05 出现 CPU 异常"，范围却选了单台主机。case03 另外三台主机一天前约 66%、两天前约 48%，现在 84%~88%，都在涨，但都没过阈值，模型就当成了正常。加上"1 天前"的值之后，这个判断也没有变。
- **只看最近 60 分钟**。工具默认窗口是 60 分钟，case02 的 OOM 发生在 10 小时前，内存曲线是 10 小时一个周期的锯齿。模型两轮都没有把窗口调大，看到"导出缓存未清理"的日志，却把它归到了两天前的发布。
- **分析对了，标签贴错**。case07 两轮都找到了"node-agent 升级到 v1.9.0 改用 cgroup v2 采集"，也看到 Redis 实际只用了 3.2G/8G，结论却选了配置变更，而不是监控误报。

只在一轮出现的问题，主要是模型读工具输出时的随机性：

- case04 第二轮把 `compare_peers` 读错了，说同在 az-c 的 pay-03"延迟正常"，实际是 42ms；
- case06 第二轮搜日志时加了关键词 "disk io"，把备份日志过滤掉了，没找到原因，转而怀疑监控数据。

结论：

- 4 个工具的设计是够用的。必需工具覆盖两轮都是 100%，case05 还会顺着日志去查数据库 `mysql-inv-01` 的变更。错误集中在"读数据"和"下结论"两步。
- 8B 思考模型在同样的输入下，两轮结果能差很多，每个 case 只跑一次，不足以判断提示词改动是否有效。上面第二轮的两处改动没有看出效果，留在代码里是因为它们让工具输出和类别语义更完整。
- 成本：每个 case 大约 4~5 次 LLM 调用、1.5 万 tokens、2~7 分钟，单次调用最慢超过 3 分钟，主要是思考模式拖慢的。

可以继续做的：

- 每个 case 跑 3~5 次，取平均值和方差；
- 影响范围改成用 `compare_peers` 的数据按规则计算，不交给模型判断；
- `search_logs` 按关键词没有命中时，提示"不加关键词有 N 条"；
- `query_metrics` 的"前一天同时段"同时给出最大值；
- 换更大的模型做对比。

## 测试

`tests/test_ops_agent.py` 用剧本模型离线运行，覆盖：case 数据自洽（告警值和生成的指标对得上）、7 个 case 的可解性、4 个工具的过滤和匹配规则、正常收敛、到达轮数上限直接出报告、报告解析失败、评分函数。
